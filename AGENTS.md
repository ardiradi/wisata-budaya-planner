## Non-negotiable truth and feasibility rules

- Never invent a destination identity, historical/cultural fact, price or opening hour. No model knowledge, fixture or search snippet counts as verification.
- Recommend only approved canonical place IDs for the selected city. Preserve evidence references at field level and honor source revocation, conflict, expiry and licensing.
- Keep `verified`, `estimated`, `unknown`, `stale` and `conflicted` distinct. Estimates require a reviewed deterministic method and a visible range/assumption. Identity, history and opening hours cannot be estimated.
- Never replace unknown prices with zero or unknown hours with defaults. Food tags, names, ratings and cuisine do not prove halal status, allergy safety or accessibility.
- AI returns allowlisted selections and reason codes. Domain code owns schedule, costs, provenance rendering, route validation and feasibility. Do not display unvalidated model facts or raw model prose.
- `validated` means checks pass under disclosed estimates at a recorded time; it does not guarantee future conditions. Unknown essential evidence cannot pass. A draft, blocked explanation or empty result is better than fabricated certainty.
- Hard user constraints and locks cannot be relaxed automatically. Edits create immutable revisions and must revalidate; preserve the last valid version.
- Keep all necessary meals budgeted except explicitly documented traveler-provided/prepaid portions. No general meal out-of-budget exclusion. Include all walking components per traveler and satisfy explicitly mandatory interests. Resolve factual authority through explicit field heads/current ordered reviews, never latest-verified fallback; follow [M1 contract decisions](docs/m1/CONTRACT_DECISIONS.md).
- Use destination IANA timezones and integer currency amounts with explicit charge units. Include outbound/return travel and party costs; use dates as the duration source of truth.

## Architecture and code standards

- Build a modular monolith with narrow interfaces. Keep planning/validation functions pure and independent of Next.js, database and provider SDKs.
- Keep provider-specific payloads inside adapters. Validate every external boundary at runtime; TypeScript types alone are insufficient.
- Prefer small cohesive modules, explicit error/result types, dependency injection at boundaries and configuration over scattered magic values. Add abstractions only when they protect a real boundary.
- When persistence implementation is separately approved, use schema migrations and reviewed PostgreSQL constraints/RLS. Authorize parent and child objects independently of user-supplied ownership values. Server actions and RPCs are security boundaries. Phase B3 does not implement production storage, migrations, durable saving or authentication.
- Preserve city/currency/locale/timezone configuration for expansion. Do not hardcode Palembang throughout algorithms or promise unsupported transport modes.
- Use supported, compatible dependencies and a lockfile; local Phase B3 dependencies remain authorized. Check official documentation for changing API and hosting behavior. Document meaningful tradeoffs without provisioning services or configuring actual providers.
- Scope changes tightly; avoid unrelated refactors and generated boilerplate. Keep user-facing flows free of internal implementation jargon.

## Security, privacy and provider use

- Keep OpenAI, database privileged and routing-server secrets out of browser bundles, logs, Git and documentation. Never print secret values. Use separate environment projects and least privilege.
- Apply deny-by-default ownership policies and public catalogue projections. Test guest/account cross-owner access, including nested versions/items and race conditions.
- Treat prompts, preference text, URLs and evidence content as untrusted. No model-generated SQL/tool/URL execution; safely render all text.
- Keep private responses out of shared caches. No real PII in tests, preview data or raw prompt logs; minimize location and sensitive preferences sent to providers.
- Do not assume Google or other third-party content may be retained, put into prompts, copied to fixtures, stored in backups or embedded permanently in itinerary versions. Follow the approved field-level policy and attribution requirements.
- Use centrally bounded timeouts/retries and transactional spend reservations. Count all attempts, including SDK retries and uncertain charges; fail closed when authorization/spend state is unavailable.
- Implement the approved deletion/retention policy, including backup restore replay. Do not promise zero provider retention because `store: false` is configured.
